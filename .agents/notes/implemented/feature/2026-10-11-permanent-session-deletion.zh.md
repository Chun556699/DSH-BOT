# Agent Note: 永久删除 Session

Status: implemented

[English](2026-10-11-permanent-session-deletion.md) | 中文

## 问题

归档隐藏 Session，但保留其历史与文件。永久删除操作需要可靠的所有权规则：Session 的工作目录可能包含共享项目文件，活动写入者也可能在清理期间重新创建文件。

## 决策

Session Controller 在用户确认后仅删除持久化提供方所属存储。它通过已有归档活动提供方拒绝仍在运行的工作，阻止 API 激活，并等待 API 持有的 Agent 句柄完成 dispose，再请求持久化提供方删除。冷态 Session 无需激活；其他活动所有者或写入者会被拒绝。

JSONL 提供方负责移除编码后的 Session 目录及其全部代际，并保持进程内与内核写入排他。嵌套链接只移除链接本身，不遍历目标。每次移除都经由删除过程已打开的目录解析：Linux 使用 `/proc/self/fd` 路径，Windows 以拒绝重命名的句柄固定每个目录。因此删除期间目录被替换时会拒绝执行。两种机制都不具备的主机报告 `supportsDeletion: false`。获取锁时从不截断锁文件，并拒绝链接形式或带多个硬链接的锁路径。POSIX 上的锁 inode 保留到全部日志被删除。随后清除 Workspace 成员关系、置顶与归档；仅在成功后移除列表条目并清除导航选择。

## 考虑过的替代方案

**删除工作目录。** Workspace 注册和 Session 元数据不证明项目文件的独占所有权。移除该目录可能破坏其他 Session 的工作。

**将归档当作删除。** 归档有意保留历史和撤销路径，无法满足永久移除需求。

**先检查每个路径，再按路径移除。** Node 不提供基于描述符的相对移除。其他进程可在下一步操作前把已检查的目录替换为链接，递归移除随后会进入链接目标。

**移除共享附件或 spill 对象。** Fork 历史可能仍引用这些对象。没有引用计数时删除它们，会破坏保留的对话。

## 后果

删除不可撤销，且可能只完成一部分。清理失败不会发布列表移除事件，但也不会恢复已删除文件或已释放的 Agent。确认框保持打开以便重试；日志已被移除的 Session 可能不再出现在刷新后的列表中。共享项目文件、附件对象、独立 spill 存储和其他 Session 均保留。macOS 和浏览器 worker 无法删除 JSONL Session。

存储、Remote、Client 列表、导航和浏览器测试验证所有权拒绝、取消、重试以及无关文件的保留。[内核租约](2026-08-31-cross-process-session-write-lease.zh.md)与[归档活动](2026-09-21-archive-stops-running-session-work.zh.md)决策仍各自适用。
